## Pass 3c — iteration 3 report (read-only; nothing edited, no issues or upstream filings)

### 1. Corrections requested

- **Ordering claim corrected.** In iteration 2 I wrote that newest-first access "is served by `resultTime=latest` or a time window". That is wrong. `resultTime=latest` returns only the observation(s) at the single greatest result time (ties included); a time window returns the matching set in the same ascending default order. CSAPI 1.0 defines no sort parameter (IDR-011 §8.1, upstream #175), so "the most recent N observations" has no standard request: a client must page ascending to the last page or repeatedly narrow a window. The research choice (ascending, P-011-06/IDR-027) stands; F-14(c) remains a documentation gap only — the Guide should state the direction — and the practical consequence above should be stated with it.
- **F-13 restrictions unapproved.** The suggestion to reject or warn on `@id`/`@link`-suffixed unknown members is withdrawn as a recommendation and recorded as an unapproved option. Deciding it requires examining the applicable extension rules first: RFC 7946 §6.1 foreign members (GeoJSON resources), the open `observation.json` schema (no `additionalProperties:false`), SensorML 3.0 extension rules, and Part 1 Req 80/93 mapping tables. F-13's confirmed content is unchanged: the example/schema discrepancy, the absence of any Guide policy for unknown inbound members, and the requirement that tests isolate the `foi@id` member from the `data:` URL defect.

### 3. New findings from the write-path reads

**F-15 — Command submission without an idempotency key.** Severity **Medium**; type: credible risk (departure from accepted research, only obliquely recorded).
- **Evidence.** `glaux-server-implementation-guide.md:505`: "Provide an optional, documented `Idempotency-Key` extension for creation and command submission… Do not require this header for all CSAPI clients." Accepted research required it for unsafe submissions: IDR-029 §8.2 ("Require for command submission/cancellation and any action that may cause a physical effect"), rec 4 [Critical], §19.1 ("Command redispatch after ambiguous response → duplicated physical effect → mandatory key"); `idr-srv-031-server-write-and-ingestion-model-report.md:266-275` ("Mandatory scoped idempotency for unsafe submission") and rec 4; IDR-037 §7.3 ("The unsafe POST profile requires a scoped idempotency key… A client timeout is not evidence of failure"). The Guide acknowledges the consequence only in a verification bullet (`glaux-server-implementation-guide.md:981`: "unkeyed ambiguity makes no deduplication promise"); §13 has no row, unlike the recorded `If-Match` departure at L503.
- **Failure scenario.** A standard CSAPI client (no Glaux header) posts a command over a DDIL link, the response is lost, and the client (or operator) resubmits. IDR-036 §7.3 correctly forbids parameter-equality dedup ("a new operator intent uses a new key even if parameters are equal"), so the server must treat the retry as a second command and dispatch twice. Server-side reconciliation (Guide L137) covers dispatch retries, not client retries.
- **Mitigation checked.** Optional key protects Glaux-aware clients (Publisher, webapp); adapters may have device-level correlation. Neither helps third-party clients, and the Goal makes DDIL operation a first-class context.
- **Smallest correction.** Record the departure and rationale (standard-client interoperability) in §13, and put one decision to the owner: whether a deployment/ControlStream-level option to require the key for command and feasibility POST exists (research's "unsafe POST profile"), default off. **Test:** unkeyed double POST yields two commands (documented); keyed double POST yields one; with the option on, unkeyed POST is rejected with a documented problem. **Timing:** before the Phase 5 command submission leaf.

**F-16 — Batch atomicity default reversed without a record.** Severity **Low**; type: optional improvement. `glaux-server-implementation-guide.md:507` chooses a bounded all-or-nothing transaction for multi-record requests; accepted IDR-031 rec 7 ("Default batches to item atomicity with complete results. An all-or-none job is a separate bounded capability") and IDR-029 §10 chose per-item atomicity. The Guide's choice is defensible for the public API — CSAPI defines no per-item result document — but the departure is not in §12.2/§13. **Correction:** one §13 row. **Test:** batch with one invalid item stores nothing and reports the failing item.

**F-17 — Stale acceptance text inside accepted reports.** Severity **Low**; type: confirmed defect (document integrity). Headers say "Accepted", but closing sections still read "In Review… not accepted for downstream use" or "acceptance remains deliberately unchecked": IDR-014b L644, 014c L663, 014e L681, 028 L526, `idr-srv-029-transaction-consistency-idempotency-and-concurrency-strategy-report.md:534`, 030 L772, 032 L495, 033 L539, 035 L606, 036 L649. **Correction:** a one-line register/Guide note that the header status controls, or normalize the text. Not blocking.
