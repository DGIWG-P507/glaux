### 2. F-12 reassessed against Guide §7.2 and issue #19

**Revised finding — F-12: runner independence rule permits shared wire types for response interpretation.** Severity **Low** (down from Medium); type: optional improvement.

- **Evidence.** Guide §7.2 already states: implement the abstract tests "as independent HTTP checks"; the runner "must not import server selection logic, serializers, or fixture-derived expected responses as its sole oracle. It may use ordinary HTTP/format libraries and pinned schemas, but expected resource relationships, query answers, and value meaning must be independently authored or calculated." Guide §8.1.1 adds "Encoder/decoder agreement alone cannot exclude a shared bug." Issue #19 (leaf 1.4.2) requires "a separately implemented HTTP test client against a real isolated listener" and "independent request/response fixtures". My 3b statement that the Guide lacked a runner-independence rule was wrong; it exists.
- **Precise remaining gap.** "As its sole oracle" forbids the server being the *only* judge but permits the runner to deserialize responses through `glaux-standards` wire structs so long as expected *values* are independent. Independent values do not catch a shared member-name or encoding misreading when both sides use one type (e.g., the `foi@id`/`samplingFeature@id` confusion in F-13 below; a wrong `@link` spelling; a wrongly optional member). IDR-050 is stricter — §6.3 "black-box cases do not deserialize through the server's wire structs", `idr-srv-050-conformance-harness-strategy-report.md:689-692` "without linking server domain or wire crates", §17 rec 3, §18.1 — and the Guide did not import that sentence.
- **Contrary evidence / mitigation checked.** Pinned schemas are used, but tagged `observation.json` has no `additionalProperties:false` and `samplingFeature@id` is optional, so schema validation would not detect an emitted `foi@id`. Issue #19's fixtures are independent for the HTTP boundary (Guide §§4.1/4.3/6.4), not for CSAPI representations.
- **Smallest correction.** One sentence in §7.2: the conformance runner interprets response bytes with generic JSON and the pinned schemas plus independently authored member names; it does not use server wire types for interpretation. **Not** a separate workspace package, and nextest stays optional (Guide §8.1.1 already says so).
- **Resolving evidence.** Runner crate has no dependency on `glaux-standards`/`glaux-domain` (compile-time check in CI). **Timing:** before #19 or the first "extend the independent runner" leaf (2.6.1).

### 3. New findings

**F-13 — Published Part 2 example uses `foi@id`, which the schema does not define.** Severity **Low**; type: unresolved question (source defect) + fixture hazard.
- **Evidence.** Published Part 2 Clause 16.1.5 third example and tagged `api/part2/openapi/examples/observations/obs-link-inline-image.json` contain `"foi@id": "55f48g48th"`. Tagged `observation.json` defines `samplingFeature@id`, `datastream@id`, `procedure@link`, `result`/`result@link`; no `foi@id`. Grep of the whole corpus for `foi@id`: no hits; register row #83 records only the `data:` URL; Guide §13 has no row.
- **Failure scenario.** A fixture author copies the published example; the server (or a shared wire type, see F-12) accepts/emits `foi@id`; the permissive schema passes; observation→sampling-feature linkage silently disappears for that record.
- **Mitigation checked.** Guide §4.3/§4.4 name `samplingFeature@id` indirectly via the schema; nothing warns about the example.
- **Correction.** §13 row: never emit `foi@id`; treat inbound `foi@id` under the unknown-member policy; fixtures derived from that example are corrected and labelled. **Test:** negative fixture posting the published example → documented rejection/ignore outcome. **Timing:** before the Phase 3 observation representation leaves.

**F-14 — Accepted query/relationship interpretations not carried into the Guide.** Severity **Low**; type: confirmed documentation gap (a), unresolved questions (b, c). Same pattern as F-07a/F-11.

(a) **Root `parent` filter vs top-level default.** Part 1 Req 11 B: with `recursive` omitted, `/systems` "SHALL only include the top-level systems"; Req 42 B: `parent` returns "only subsystems of a parent system…"; example `/systems?parent=4g4ds54vv`. Literal composition yields an empty set; ATS A.47 ("for each System resource in the returned collection…") passes vacuously on an empty result. Same for Deployments (Req 21 B vs Req 47 B, A.52). IDR-011 §7.5 and accepted P-011-05 resolve this (explicit `parent` is a direct-child query regardless of the root default). `glaux-server-implementation-guide.md:735` says only "Root lists use the standard top-level/default-recursion behavior"; L752 gives no exception; §13 has no row. **Mitigation:** Guide §8.1.1 "check exact identities" and the L944 parent/child fixture reduce the runtime risk if applied. **Correction:** §13 row citing P-011-05; adapted A.47/A.52 must include a known-hit assertion. **Timing:** before the Phase 2 hierarchy/filter leaves (group 2.5).

(b) **Write-side form of `deployedSystems` link `href`.** Part 1 Tables 43 and 52 footnote: "When inserting or modifying a link to a system stored locally, the link url (href property) shall be set to the uniqueID of the system"; the published Deployment example (a read response) uses a canonical URL plus `uid`. `ogc-connected-systems-upstream-history-register.md:146` records the rule (routed to 010/017); IDR-017 §9.1 says `uid` "is never… a substitute for resolving `href`"; IDR-011 P-011-15 covers query-side matching by ID/UID/href. The Guide contains no `deployedSystems`, `uniqueID`, or accepted-href-form rule (grep). **Scenario:** a peer client or fixture sends `href` = URN UID (per footnote) and the server accepts only URLs, or the reverse; interoperability and fixture disagreement. **Correction:** one sentence in §4.6 or §13: accept UID or canonical local URL for local targets, resolve to one identity, emit canonical URL plus `uid` on read. **Timing:** before the first Deployment create/replace leaf.

(c) **Default observation order direction.** `glaux-server-implementation-guide.md:444`: "result time then ID" — direction unstated. Accepted P-011-06 and IDR-027 L77/§8.3 fix **ascending**, flagged provisional pending 014A–G; 014a notes OSH `order=desc`, 014c notes pygeoapi ascending by phenomenonTime; no later revisit found in Guide/Roadmap. **Consequence:** default `GET …/observations` (limit 10) returns the ten oldest records. **Correction:** state the direction in §4.4 (either confirm ascending or record a deliberate change as a §13 decision — the owner's call); paging fixtures must encode it. **Timing:** before the 3.3.x observation listing leaf.
