### Findings

**F-07 — `resultTime=latest` semantics diverge from the reference implementation and the divergence is unrecorded**
- Severity/type: Medium–High, credible interoperability risk (plus documentation omission).
- Evidence: Part 2 Requirement 50 D says only observations "with the latest result time SHALL be included" — silent on grouping. Guide §4.4 (`glaux-server-implementation-guide.md:440`): "select the greatest visible result time and retain ties" within endpoint scope; Roadmap 3.3.5 (`glaux-server-roadmap.md:403`) tests "independently expected maxima" on root and single-stream fixtures. OSH (`MVObsStoreImpl.getObsStream`, `InMemoryObsStore` class doc, `ObsFilter.withLatestResult()`) returns the latest observation *per datastream/FOI series*. IDR-011 considered per-datastream grouping and rejected it as "not baseline"; Guide §13 has no row for this.
- Failure scenario: a client calls `/observations?system=X&resultTime=latest` to get current values for all of X's streams. Glaux returns only the stream(s) that happened to report last; OSH returns one per stream. Same query, different answers, both "conformant". Test 3.3.5 then hard-codes the literal reading as the "independent expected answer".
- Contrary evidence checked: the literal text does support the Glaux reading; ATS A.50 does not test `latest`, so neither reading fails conformance; CS-GO's latest test seeds a single datastream, so it does not discriminate; upstream #64/#88 addressed `earliest`/`now`, not grouping.
- Smallest correction: add a §13 row recording the divergence from OSH and choose explicitly — either per-series semantics on multi-stream endpoints, or literal semantics with a documented deviation — and file an upstream clarification (owner is already a collaborator; see #201). Amend 3.3.5's Done text accordingly.
- Resolving evidence: a two-datastream fixture with different latest times whose expected result set is written down before implementation; one run through an OSH-based or OWSLib client.
- Timing: before #112 (3.3.5); ideally as a Guide change before Phase 3 opens.

**F-08 — Part 1 ATS prerequisite lists conflict with the normative dependency statements and Guide §1.2 does not record it**
- Severity/type: Medium, unrecorded source inconsistency.
- Evidence: 23-001 Annex A, test A.2 (`/conf/api-common`) lists prerequisites `ogcapi-common-2/1.0/conf/collections` and `…/conf/simple-query` (OGC API – Common Part 2) and malformed URIs (`spec/ogcapi-1/1.0/conf/core`; A.11/A.12 `ogcapi-4/1.0/…`; A.13 `ogcapi-1/1.0/conf/geojson`). The requirements class itself depends only on Common Part 1 core/landing-page/json and Features Part 1 core. Guide §1.2 states the "exact dependencies" and says no Common Part 2; §13 has no row. Docs grep: no mention of Common Part 2 prerequisites anywhere except IDR-014B line 248, which judges CS-GO's Common Part 2 URI "misaligned" — arguably unfair given the ATS.
- Failure scenario: 2.6.1 (#80, prerequisite tests) is authored from the Guide; a reviewer or a future executable suite built from the ATS expects Common Part 2 collections/simple-query evidence Glaux never targeted; the conformance declaration is then disputed on paper.
- Contrary evidence: practical delta is small — Features Part 1 core already requires `/collections` and `bbox`/`datetime`/`limit`, so behaviourally Glaux will largely satisfy those classes anyway.
- Smallest correction: one §13 row recording the ATS prerequisite defects and the decision to follow the requirements-class dependency statements; reword IDR-014B:248.
- Resolving evidence: 2.6.1 test plan cites both the class dependencies and the §13 row.
- Timing: before #80.

**F-09 — ATS path defect `deployedSystems?recursive=true` not in the recorded overlay**
- Severity/type: Low, unrecorded ATS defect.
- Evidence: 23-001 tests A.53/A.55/A.56 use `{deploymentCanonicalUrl}/deployedSystems?recursive=true`; the requirement path is `/deployments/{deploymentId}/systems` (OWSLib also uses `deployments/{id}/systems`). IDR-011 §14.3 records `/components`, `/controls/{id}`, `/command/{cmdId}/status`, etc., but not this one.
- Failure scenario: 2.6.2 (#81) test author copies the ATS path; test fails and someone adds an alias route to "pass".
- Smallest correction: add the row to IDR-011 §14.3 / Guide §13.
- Timing: before #81.

**F-10 — Nine broken source links in IDR-011**

- Evidence: recursive search of all `Docs/**/*.md`: 268 references to the correct hash `8e03b236a049849f2ccc24b4fd9fdce5ff69bed2`; 9 lines in idr-srv-011…report.md use a 38-character truncation (`8e03b236a049f2ccc…`) that 404s. No truncated pins in the Guide or Roadmap.
- Smallest correction: fix the 9 links.
