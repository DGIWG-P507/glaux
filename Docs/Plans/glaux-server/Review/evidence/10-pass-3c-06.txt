## Pass 3c — iteration 6 report (read-only; nothing edited, no issues or upstream filings)

### 1. F-18 — primary-source checks completed; finding narrowed

**Ownership is specified; my earlier statement is withdrawn.** The pinned `controlStream.json` (tag `8e03b23…`, `api/part2/openapi/schemas/json/`) distinguishes the two fields:
- `live`: `oneOf [null, {boolean, readOnly: true}]`, description "Flag indicating if the command channel can currently accept commands", listed in `required` — server-derived and nullable.
- `async`: plain `boolean`, no `readOnly`, listed in `required` — client-supplied.
- `schema`: `writeOnly`; `system@link`, `controlledProperties`, `issueTime`, `executionTime`: `readOnly` (several nullable).

`glaux-server-implementation-guide.md:418` governs exactly this: "Maintain explicit request projections for server-generated/read-only members and response projections for write-only members… Clients need not supply generated IDs, server-generated parent links, format lists or derived summaries." Issue #156 (5.1.1) requires "generated stream metadata", forbids "generated-field input requirements", and its verification submits "one write-only schema without generated ID, parent links or format lists". So `live` is Glaux-derived and `async` is client-set; nothing is unspecified there.

**Published requirement vs research policy.** The tagged Clause 9 attribute table defines `live` as "Indicates whether the control stream currently accepts commands" (Required) and `async` as "Indicates whether commands are processed asynchronously" (Required); the clause prose says a ControlStream "can be used to provide access to real-time commands only, archived commands only, or both", disambiguated by its metadata. No published requirement states what a POST receives when `live` is `false`. The `409`-before-creation rule in IDR-037 §6.3 is labelled [N/E/P] — a proposed Glaux policy, not a CSAPI obligation.

**Narrow remaining question (Low; unresolved question, owner decision).** Guide §§4.9/6.4 and the owning leaves #163/#164 do not say what happens on a Command POST when Glaux's own `live` value is `false` (or `null`):
- **Command:** rejection before creation is well-motivated — the stream advertises that it does not currently accept commands, and admitting one contradicts the server's own published metadata. Options are the research's `409` or a documented alternative; either must leave no resource or work.
- **Feasibility:** needs its own justification. `live` is defined only for command acceptance; §11 does not tie feasibility to it. Analysing a future command against a currently non-accepting stream can be legitimate planning if an evaluator exists, or meaningless for an archive-only stream with no executor. IDR-037 applies `409` to both for simplicity; the Guide should choose explicitly rather than inherit that by default.
- **Adjacent sub-point:** the rule that derives `live` (when it is `false`, when `null`) is not stated; the runner needs it to construct a non-live fixture.
- **Not implied:** IDR-036's internal stream states (`draft/active/suspended/…`) are not adopted by the Guide and are not part of this finding.

**Correction:** one sentence in §4.9 (or a §6.4 table row) stating the Command outcome, the Feasibility outcome, and the `live` derivation; add the case to #163's Done text. **Test:** non-live fixture → documented outcome with zero Command/status/work rows; `live=null` → documented outcome. **Timing:** before #163.
