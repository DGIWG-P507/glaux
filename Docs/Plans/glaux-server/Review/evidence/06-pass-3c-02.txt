### 2. F-14 reassessed

**(a) Root `parent` filter — accounting for #71/#72.** Issue #71 says: "Independently tabulate expected IDs from Part 1 hierarchy/filter requirements, Guide §§4.2/6.2–6.3 **and IDR-011's root-parent interpretation**… Compare root defaults, **explicit root parent**, nested direct children and recursive descendants; direct parent remains direct with recursion enabled… demonstrate that… **an ignored parent predicate is detected**." Issue #72 requires exact IDs for "root/nested defaults, explicit parent and applicable System selectors". So the leaves already carry P-011-05 and demand a known-hit assertion, which closes the vacuous-pass hazard (ATS A.47/A.52 pass on an empty set) at the leaf level. What remains is documentation consistency: the same issues state that "later Guide decisions control" over IDR-011 project choices, yet `glaux-server-implementation-guide.md:735` states only the plain top-level default and §13 has no row, so the Guide and the leaves rely on different documents for the expected answer. **Revised:** Low, optional improvement — one §13 row citing P-011-05 (Req 11 B/21 B vs Req 42 B/47 B); no change to #71/#72. Separately, the ATS overlay used by the runner leaves should record that A.47/A.52 need a non-empty known-hit check (IDR-011 §14.3 corrects only the ID comparison).

**(b) `deployedSystems` link `href` on write — three distinct things.**
- **Required:** accept a UID-form `href` (URI/URN) for locally stored Systems in GeoJSON `deployedSystems@link[]` and SensorML `deployedSystems[]` on create/replace/patch, resolving by UID. Basis: Table 43/52 footnote "the link url (href property) shall be set to the uniqueID of the system to be linked", incorporated by Req 84 and Req 98 ("SHALL implement the mappings specified in Table 42 and Table 43" / "Table 51 and Table 52"); register `ogc-connected-systems-upstream-history-register.md:146` (closed via PR #92). A standards-following client sends exactly this form; external systems keep an external URL.
- **Optional compatibility (project choice to record):** also accepting a canonical local URL `href` (the form shown in the published *read* example and likely from peers). If adopted, it must resolve to the same identity; if not, the rejection must be documented.
- **Optional response metadata:** emitting `uid` beside `href` in returned link objects. The shared Link schema permits `uid`; the published example shows it; IDR-017 §9.1 treats `uid` as a hint, never the authority.
- **Gap:** the Guide states none of the three (no `deployedSystems`, `uniqueID` or href-form text). **Severity Low; type:** confirmed documentation gap for the required item, unresolved question for the two optional items. **Correction:** one §4.6/§13 sentence covering all three. **Test:** POST/PUT Deployment with UID-form href → success and read-back resolves to the System; URL-form and unknown-UID variants → the documented outcome. **Timing:** before the first Deployment create/replace leaf.

**(c) Default observation order.** Treated as settled research: ascending `(resultTime, ResourceId)` per accepted P-011-06 and IDR-027 L77/§8.3. I found no grounds to revisit: 014A–G recorded no recommendation to change (014a notes OSH offers optional `order=desc`; 014c notes pygeoapi ascending by phenomenonTime), and newest-first access is served by `resultTime=latest` or a time window. Remaining gap is only that `glaux-server-implementation-guide.md:444` omits the direction; paging fixtures need it. **Low; optional improvement:** add "ascending" to §4.4.

### 3. F-13 restated with the two problems separated

1. **Example/schema discrepancy (source defect).** Normative Req 97 `/req/json/observation-schema` requires validity against `observation.json`, whose mapped member is `samplingFeature@id`. The published Clause 16.1.5 example and tagged `obs-link-inline-image.json` use `foi@id`, which is informative text and merely schema-permitted as an extra member. Schema controls; the example is defective and unrecorded in the corpus/Guide. Whether to report it upstream is the owner's decision.
2. **Input-handling policy (separately justified).** The Guide has no general rule for unknown/foreign members in inbound resource JSON — `glaux-server-implementation-guide.md:406` ("preserve permitted extensions without allowing them to replace… validated relationships") and `glaux-server-implementation-guide.md:410` ("permissive acceptance of an unknown member is not validation") are the nearest statements. So the fate of `foi@id` on POST — preserved as an extension (silent loss of the sampling-feature association), ignored, or rejected — is currently undetermined. This decision stands on its own and should be made explicitly; my recommendation is to reject or at least warn on `@id`/`@link`-suffixed members that are not mapped members, because they mimic reserved association syntax.
3. **Test isolation.** Baseline: a valid observation with `samplingFeature@id` and a plain result → success and the association is present. Variant: identical except `foi@id` replaces `samplingFeature@id` → the policy outcome, with any problem detail naming `foi@id`. Control: the same published example's `data:` URL result (register #83) is tested separately so a rejection cannot be misattributed to the field name. Never emit `foi@id`.
