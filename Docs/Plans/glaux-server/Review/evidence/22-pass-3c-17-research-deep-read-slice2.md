## 2. What Sections 9-21 contain

Unlike slice 1, this remainder is substantive rather than procedural. Sections 9-16 are findings sections: schema-aware document redaction (9), observation/latest-value/cache policy (10), streaming publication policy (11), command/affordance policy (12), source trust/provenance/federation (13), DDIL and cross-boundary sharing (14), error/OpenAPI/telemetry/audit implications (15), and test implications with ten core invariants (16). Sections 17-21 are the downstream handoff matrix, recommendations split into an adopt-now slice and an explicitly deferred list (18), risks and open questions (19), success-criterion validation (20) and references (21).

The report proposes a typed policy model — `PolicyAssertion`, `PolicyBinding`, `DisclosureDecision`, `DerivedViewProvenance` — with a three-state decision envelope, an approved transform registry and bilateral federation mappings. Guide v1.3 contains none of that vocabulary: a search for `PolicyBinding`, `PolicyAssertion`, `DisclosureDecision`, `DerivedView`, `PEP`, `PDP`, `INDETERMINATE`, `caveat`, `releasab` and `securityConstraints` returns no hit in the Guide body. IDR-040 is cited at Guide lines 592 and 610 only. The accounting below therefore separates the report's **invariants**, which the Guide largely does adopt in its own vocabulary, from its **machinery**, which the Guide does not.

## 4. Not adopted, as a recorded scope choice rather than a defect

Guide v1.3 does not implement IDR-040's typed policy machinery: the `PolicyAssertion`/`PolicyBinding`/`DisclosureDecision`/`DerivedViewProvenance` records (§§9.1, 9.3, 13, 18.1 items 1-2); three-state decisions with `INDETERMINATE` and quarantine (§§13.2, 14.1); the approved transform/generalization registry (§§9.2, 18.1 item 5); bilateral federation vocabulary mappings (§13.3); the SensorML `securityConstraints`-to-PolicyAssertion mapping (§9.1); and per-profile OpenAPI derivative documents generated per authorized view (§15.2).

This is not treated as a departure requiring correction, for three converging reasons:

1. **The report itself defers the regime.** §18.2 explicitly defers the policy-engine product, policy administration, production vocabularies, operational label/caveat adapters, accredited cross-domain integration, transitive federation trust and automatic release under relaxed policy. §18.1 asks for neutral records and seams first, and §20 states the report "does not authorize IDR-SRV-041, implementation, a production policy regime, or any cross-domain deployment."
2. **The Guide states the corresponding boundary deliberately.** Line 610 declines to select a labeling adapter and refuses both a universal per-field marking rule and permission to remove required markings; line 592 assigns policy ownership, release authority and accreditation to the deploying organization.
3. **The review already dispositioned this category.** F-03 records that "a universal policy engine and research-specific approval/lease machinery are not automatically needed." Iteration 16 recorded the parallel IDR-038 instance under the same finding.

Where the Guide takes a narrower route it supplies a coherent substitute: instead of per-view OpenAPI derivatives it emits one implementation-specific description of the **enabled deployment** (line 362), requires the declared class list, OpenAPI, routes, representations and runtime configuration to stay consistent (line 907), and protects schema and capability disclosure at runtime (lines 598, 600). IDR-040 §9.4's rule that a restricted representation may claim only the conformance it satisfies is therefore met in its positive form at line 907: declare a class only when the enabled implementation satisfies all applicable requirements with adequate tests.

## 5. One evidenced gap: response cache validators and variants (§10.4, and the "cache" member of §16.3 invariant 6)

This is the single item in Sections 9-21 where the Guide's own stated principle has a channel it does not cover.

**What the report asks for.** §10.4: "Every representation cache key and validator includes the authorized-view identity, target profile/media type, relevant binding/policy/trust epochs and transform version. Shared caches must not serve one requester's representation to another context. `Vary` is used where HTTP negotiation is sufficient, but sensitive authorization state is not placed in public headers; server-side partitioning remains mandatory." §16.3 invariant 6 lists "a cache, cursor, subscription or queued decision cannot outlive its policy/trust bounds."

**What the Guide says.** The Guide adopts the cursor, subscription and queued-decision members of that invariant (lines 471, 547, 647) and omits the cache member. Its only caching-adjacent statements are: RFC 9110/9111 named as an inherited dependency (line 258); strong representation-specific ETags for concurrency control, with `412` on stale preconditions (line 503); and "Use appropriate `Vary` headers and representation-specific ETags" in the content-negotiation rule (line 739). A search of the whole Guide for `cach` returns only lines 258, 594 (issuer-key caching) and the negotiation reference. No `Cache-Control`, `private`, `no-store`, shared-cache or cache-partitioning rule appears, and no statement binds a validator or cache key to the authorized view. The disclosure channels enumerated for testing — "links, schemas, counts, latest selection, or events" (line 1019) and the delivery/exchange checks (line 983) — do not include cache validators.

**Why the inherited standard does not close it.** RFC 9111 §3.5 provides that "A shared cache MUST NOT use a cached response to a request with an Authorization header field to satisfy any subsequent request unless the response contains a Cache-Control field with a response directive that allows it to be stored by a shared cache." That protection is keyed to the `Authorization` header specifically. §5.2.2.7 defines the `private` directive that would otherwise prevent shared storage, and the Guide never instructs the server to emit it. §4.1 makes `Vary`-based selection match only "request header fields nominated by that Vary field value," so an authorized-view distinction that is not expressed in a nominated request header is not part of the cache key.

**Concrete consequences.**

- *Validator as an inference channel.* If the ETag is computed over stored resource state rather than over the emitted authorized representation, a caller whose view conceals a field can detect concealed changes by polling: the visible body is unchanged while the validator changes, or a conditional request returns `200` where `304` was expected. That is precisely the class of leak the Guide already commits to closing at lines 469 ("Protected information must not simply be substituted with NULL: apply §4.10's denial/concealment policy to prevent membership, null tests, errors or counts revealing it"), 803 and 975. The Guide's phrase "representation-specific" at lines 503 and 739 plausibly covers format and profile variance; whether the authorized *view* counts as a distinct representation is not stated either way, so the outcome is unspecified rather than wrong.
- *Cross-caller reuse in a deployment shape the Guide supports.* The Guide contemplates a trusted reverse proxy that supplies forwarded headers (line 364) and TLS termination (line 596), and permits an explicit read-only anonymous deployment (line 596). Where a caller's authorization derives from something other than an `Authorization` request header — a client certificate, or an identity header injected by that trusted proxy — RFC 9111 §3.5 does not apply, no `private` directive is emitted, and the distinguishing input is not among the `Vary`-nominated request headers. An intermediary may then serve one caller's authorized representation to another context.

**Weight and home.** This is a documentation gap with an evidenced consequence, not an unadopted optional mechanism: it concerns the Guide's own concealment commitment rather than IDR-040's policy machinery, and it survives the scope reasoning in Section 4 because it needs no policy model to fix. It is recorded as a related instance under **F-03**, whose residual question is already "selected action/scope/inheritance/source-binding/concealment semantics," rather than as a competing finding number. Closing it needs one Section 4.10 or Section 6 sentence (bind validators and any cache key to the authorized view; emit `Cache-Control: private`, or `no-store` for authorization-dependent representations), plus one line added to the line 1019 disclosure-channel test list. No new capability is implied.

## 6. Observations recorded, not findings

- **Audit field list (§15.3).** IDR-040 requires the audit record to capture decision/correlation ID, actor/workload, action, protected resource reference, source/effective binding versions, policy/trust epochs, outcome, existence/content disposition, transform, recipient/domain/purpose, PEP, time, reason reference, outbound gateway status and integrity evidence. Guide line 602's floor is narrower (verified actor/source, operation, target/revision, time, outcome, correlation identifier), and the additional fields are the ones bound to the unadopted policy model. This is the same disposition already recorded under F-20 in iteration 16 from IDR-038's event catalog; no second instance is added for the same question.
- **Supporting evidence for `fq-09`.** §10.3 ("A visible heartbeat or absence of one is also a disclosure. Health endpoints intended for infrastructure therefore expose only a minimal service-health contract") and §15.3 ("public health surfaces reveal only deployment-approved service state") supply the research basis for the metrics/traces exposure question raised in iteration 16. This report is added to that question's evidence; the question itself remains noted and unscheduled.
- **CS-Go repository URL inconsistency.** IDR-040 §21.3 cites Connected Systems Go as `https://github.com/opensensorhub/connected-systems-go`, whereas IDR-037 Appendix B, IDR-038 Appendix C and IDR-039 §22.2 all pin `https://github.com/SomethingCreativeStudios/connected-systems-go`, as does Guide line 1129. Which URL is correct was **not** verified: resolving it belongs to the separate `peer-source-spot-checks` remaining check, which pins CS-Go anyway. Recorded as `fq-10` so the discrepancy is not lost. It is not asserted to be a defect and is not attached to F-10, whose subject is the distinct IDR-011 malformed-commit-hash links.
