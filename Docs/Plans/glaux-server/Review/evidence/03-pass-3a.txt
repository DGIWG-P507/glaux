## Reassessment of earlier findings

**F-03 (authorization model) — revised, downgraded to Low–Medium.**
Issue #22 does require "an independent action/source/resource access matrix from Guide §4.10, with two distinguishable source groups and explicit allowed, denied and unavailable decisions", plus forged-authority, policy-outage fail-closed, and inverted-predicate checks. Those are genuine mechanism-level checks, independent of the code. What remains open is narrower than I stated: §4.10 ([guide L590–L611](Docs/Plans/glaux-server/glaux-server-implementation-guide.md#L590-L611)) gives principles ("configured caller/group/source permissions and resource relationships"; publishers restricted to "assigned Systems/streams") but does not enumerate the action vocabulary, the scope unit (System subtree, stream, collection), inheritance to nested resources, how a "source" is bound to a caller, or concealment-vs-denial. Accepted research already proposes a concrete model (final report §13.2: RBAC + resource/action/context rules; ALLOW/DENY/INDETERMINATE with indeterminate denied; SourceAssertion / PolicyBinding / DisclosureDecision separation), which the Guide deliberately did not import (§12.2: "no universal policy or trust engine"). Consequence: the matrix rows in #22 will be the first written record of the policy semantics, and "later owning tasks extend domain-specific cases" from it. Smallest correction: one approved paragraph (Guide §4.10 or the #22 execution record before execution) fixing actions, scope units, inheritance and source binding, referencing IDR-039/039A/040. Timing unchanged: before #22.

**F-06 (exchange protocol) — withdrawn as a finding.**
Consumers are planned: configured peer instances or authorized files (Guide §4.11: "administrative export/import adapter for configured peers or authorized files"), the SSE snapshot-to-live bootstrap (8.2.5, 8.4.3) and MQTT recovery (8.4.4); Goal §5.8 requires "intermittent synchronization, constrained exchange". Phase 8.3 (migrations, restore, epochs/fencing, retention, config, shutdown) is ordinary recovery work, not exchange cost. Retained only as a note: the peer consumer is another Glaux instance, which the Guide already labels an integration format, not a CSAPI representation.

**F-07 (`resultTime=latest`) — split and restated.**
- Recorded in research: yes. IDR-011 rows `idr-srv-011-query-filtering-sorting-pagination-and-selection-semantics-report.md:297-298` ("Standard does not state canonical endpoint grouping explicitly" / "Project interpretation; per-stream grouping is not baseline"), `idr-srv-011-query-filtering-sorting-pagination-and-selection-semantics-report.md:400`, `idr-srv-011-query-filtering-sorting-pagination-and-selection-semantics-report.md:868`, P-011-03 accepted 2 Aug 2026. IDR-011 L742 also records that ATS A.50 omits `latest` and prescribes supplemental tests.
- Confirmed gap (Medium, documentation): Guide §4.4 states the rule as settled and §13 — which claims to record "known consequential seams in one place" — has no row, even though the research itself labels it a project interpretation.
- Provisional (credible interoperability risk): the editor's implementation (OSH) selects latest per datastream/FOI series. Peer behaviour does not settle normative meaning, and A.50's silence means conformance is undetermined under either reading, not established. Supported query for the scenario: `GET /observations?foi={sf}&resultTime=latest` (Req 51 `foi` + Req 50D) or `GET /observations?resultTime=latest` (Req 14), where two datastreams observe the same sampling feature with different latest result times — Glaux returns only the later stream's observation(s); a per-series server returns one per stream. The standard's only `latest` example is nested (`/datastreams/123/observations?resultTime=latest`), where both readings coincide.
- Smallest correction: §13 row (interpretation + noted divergence); 3.3.5 Done text to require a multi-stream fixture on the canonical endpoint; an upstream clarification is an owner decision, not something I will file. Timing: before #112.

Severity Low–Medium; correction: §13 row citing IDR-006/008; timing before #80.

**F-09 (`deployedSystems`) — path claim withdrawn; finding restated.**
I cannot substantiate a normative `/deployments/{id}/systems` requirement — there is none. Part 1 Clause 11.4 defines only `/deployments`, `/deployments/{id}`, `/deployments/{parentId}/subdeployments` (Req 19) and `/systems/{sysId}/deployments` (Req 17); the tagged Part 1 OpenAPI has no other deployment path; Tables 43/52 encode `deployedSystems` inline (`properties/deployedSystems@link` array; SensorML `deployedSystems[]`); register issue #30 records that a separate `DeployedSystem` resource was rejected. OWSLib's `deployments/{id}/systems` is client-library behaviour, not normative. The actual conflict: ATS A.27 ("If the Deployment resource contains a link with relation type deployedSystems … Issue an HTTP GET request to the link URL") and A.53/A.55/A.56 (`{deploymentCanonicalUrl}/deployedSystems?recursive=true`) presume a dereferenceable endpoint that no requirement or encoding table defines. Research (IDR-010/017/021) follows the inline encoding correctly, but IDR-011 §14.3 records only A.53's `foi`/`system` copy error (`idr-srv-011-query-filtering-sorting-pagination-and-selection-semantics-report.md:734`), not this. Revised correction (Low): add the row to the ATS overlay with the qualified interpretation (inline array is the encoding; the ATS dereference steps are satisfied by reading it; Table 13 requires a parent Deployment's `deployedSystems@link` to include subdeployments' systems recursively — a concrete expectation for 2.5.4/2.6.2). Timing before #81.
