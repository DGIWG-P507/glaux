## 3. Question 2 — `standards-part2-inheritance`: effect of Part 2 Annex A.1 inheriting Part 1 `/conf/api-common`

### Result: **Supported.** The inheritance is real at both normative levels, is already recorded in the accepted research, and adds no inherited external class beyond those in Guide Section 1.2. Its consequence is that the F-08 qualification applies to every Part 2 resource-class declaration; the Section 13 row proposed under F-08 should say so. No new finding.

Published facts:

- 23-002 Clause 8 (`/req/api-common`): Prerequisite `http://www.opengis.net/spec/ogcapi-connectedsystems-1/1.0/req/api-common`; Requirements 1 (`/req/api-common/resources`, feature-to-resource substitution for Features Part 1 and Part 4) and 2 (`/req/api-common/resource-collection`, Features Part 1 Clauses 7.14–7.16 except 7.15.3 `bbox` and 7.15.4 `datetime`). Requirements classes `/req/datastream`, `/req/controlstream`, `/req/system-event` and `/req/advanced-filtering` list `/req/api-common` as prerequisite; `/req/feasibility` lists `/req/controlstream`.
- 23-002 Annex A.1 (`/conf/api-common`): Prerequisite `http://www.opengis.net/spec/ogcapi-connectedsystems-1/1.0/conf/api-common`. A.1 `/conf/api-common/resources`: "No test required for this requirement as it is tested in other classes." A.2 `/conf/api-common/resource-collection`: for each collection whose `itemType` is not `feature`, execute eighteen named Features Part 1 core tests (`fc-md-links` ... `f-links`). Conformance classes A.2–A.6 list `/conf/api-common` (A.4 via A.3) as prerequisite.
- 23-001 Clause 8 (`/req/api-common`): prerequisites `ogcapi-features-1/1.0/req/core`, `ogcapi-common-1/1.0/req/core`, `/req/landing-page`, `/req/json`. 23-001 Annex A.2 (`/conf/api-common`): prerequisites `http://www.opengis.net/spec/ogcapi-1/1.0/conf/core` (malformed), `ogcapi-common-1/1.0/conf/core`, `ogcapi-common-1/1.0/conf/landing-page`, `ogcapi-common-2/1.0/conf/collections`, `ogcapi-common-2/1.0/conf/simple-query`; `conf/json` omitted. This is the F-08 conflict, re-confirmed verbatim.
- Base URIs: 23-001 Clause 6.1 `http://www.opengis.net/spec/ogcapi-connectedsystems-1/1.0`; 23-002 Clause 6.1 `http://www.opengis.net/spec/ogcapi-connectedsystems-2/1.0` (Guide Section 1.2 line 262 exact).

Assessment:

1. **Transitive effect on declarations.** Declaring any Part 2 resource class (`datastream`, `controlstream`, `feasibility`, `system-event`, `advanced-filtering`) requires Part 2 `/conf/api-common`, which requires Part 1 `/conf/api-common`, whose Annex prerequisite list conflicts with its own requirements-class dependency statement. The F-08 disposition (follow the requirements-class dependency statements; record the Annex discrepancy as an adapted-test qualification) therefore covers the Part 2 declaration as well; there is no separate Part 2 conflict to resolve, and no additional external class (Common Part 2 or otherwise) becomes required through Part 2. The Guide Section 1.2 inherited-dependency table (Common Part 1 Core/Landing Page/JSON; Features Part 1 Core/GeoJSON; Features Part 4; SensorML; SWE; SFA) is complete for the Part 2 common foundation.
2. **Research already records the chain.** IDR-008 Section 7.2: "P2-01 through P2-06, directly or transitively | P1-01 | The Part 2 API/resource foundation is not standalone"; IDR-008 Section 7.3 disposes the P1-01 Annex discrepancy ("Use the coherent requirement-table prerequisites; preserve Annex discrepancy as an adapter record") and the P2-06 omission; IDR-007 line 246 carries the Part 2 `/req/api-common` prerequisite; IDR-007 P2-INT-008 records the A.6 omission. The Guide Section 7.1 rows `api-common` 1–3 (Part 1) and 1–2 (Part 2) and the Part 2 `advanced-filtering` row "plus Part 1 dependency" match the published requirement tables; the Section 7.1 closing paragraph ("a direct class is not complete while a prerequisite is unimplemented") states the transitive rule. What remains absent is the Section 13 row already requested under F-08; its wording should cover both Parts.
3. **Test-evidence consequence for the runner (3.5.1, #121; 2.6.1, #80).** Part 2 `/conf/api-common` has no test of its own beyond A.2, and A.2 is conditional on collections whose `itemType` is not `feature`. Part 2 collections are optional (Requirements 10, 16, 24, 30, 39 and 44 all begin "If the server exposes collections..."), so if Glaux exposes no Part 2 collections the class is evidenced solely by the inherited Part 1 `/conf/api-common` result; if it does expose them, the eighteen Features Part 1 core tests apply to each with the feature-to-resource substitution of Requirement 1. Either way the evidence record should say which case holds rather than report A.2 as passed vacuously.
4. **Published prerequisite discrepancy confirmed for Part 2 A.6.** `/conf/advanced-filtering` (23-002 A.6) lists only `/conf/api-common`, while `/req/advanced-filtering` (Clause 13) lists both `/req/api-common` and Part 1 `/req/advanced-filtering`. IDR-007 P2-INT-008 and IDR-008 Section 7.3 record it; Guide Section 7.1 carries the dependency. No action.

Related-instance note for F-08: the Part 2 declaration inherits the Part 1 Annex A prerequisite conflict through `/conf/api-common`; the requested Section 13 row should name both Parts, and Part 2 A.2 must be labelled conditional on exposed non-feature collections.

## 4. Additional published seams observed (overlay candidates, not findings)

1. Requirement 61 A's OpenAPI `description` says "Only command resources whose current status matches..." (copied from Requirement 58 A) while 61 B says CommandStatus; the ATS copy error therefore has a requirement-text sibling.
2. Requirement 31 B cites "Clause 7.15.2" for both `limit` and `datetime`; `datetime` is Features Part 1 Clause 7.15.4 (Requirement 41 B cites both correctly).
3. 23-001 A.66 `/conf/advanced-filtering/indirect-foi` labels its deployments step "querying deployments using transitive base properties" although it exercises `foi` (sampled-feature transitivity).
4. Every Part 2 canonical-URL test (A.5, A.12, A.19, A.26, A.35, A.40) and the Part 1 pattern it copies iterate collections with a given `itemType`/`featureType`; a server exposing no such collection has no published test of the canonical-URL requirement itself. The Glaux runner should test canonical URLs from the canonical resources endpoints as a supplemental check; this is consistent with Guide Section 7.2 line 899 and Roadmap 3.5.1 ("exercise actual routes").
5. Editorial: 23-002 A.61 "for or every"; 23-001 A.5 and A.8 list their tests out of numeric order (A.22 before A.21; A.37 before A.36). No action.
