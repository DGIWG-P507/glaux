## Adjustments from your two qualifications

**F-07 — nested endpoint is not a safe harbour.** Part 2 Table 5 makes a DataStream's `samplingFeatures` a list and Table 7 makes `samplingFeature` per-observation, so one datastream can carry observations of several sampling features. Under OSH's per (datastream, FOI) series rule, `GET /datastreams/{id}/observations?resultTime=latest` returns one observation per sampling feature; under Guide §4.4's endpoint-wide maximum it returns only the most recent one. My Pass 2/3a statement that "both readings coincide on the nested endpoint" is withdrawn. The divergence applies to nested, canonical, `foi=`-filtered and collection-items requests alike. Consequence sharpened by IDR-011 §8.2 (accepted): default order is ascending `(resultTime, RID)` and no sort parameter is baselined, so `resultTime=latest` is the only way a client obtains "newest" without paging — the interpretation therefore determines whether "newest per stream/feature" is obtainable in one request at all. Still provisional as an interoperability risk; confirmed as a §13 documentation gap.

**F-08 / F-09 — adapted vs original tests.** IDR-050 §4.2 rules 3 and 6 and §5.2 ("copied/mistargeted ATS steps need ledger adapters"; official results "retain their own suite/version/target identity") and Guide `glaux-server-implementation-guide.md:899` ("Preserve both the source procedure and the documented correction") already require the distinction. Any correction I propose for these findings assumes evidence records, per ATS case, whether the executed procedure is the published text or a ledger adaptation, and that the two are never summed. Whether the Roadmap 9.1.x reverification and claim manifest carry that labelling is deferred to Pass 5/6.

**F-11 — accounting for #56.** Issue #56 (2.3.8) requires "an expected edge list from the Guide and adopted Part 1 navigation requirements … compare exact target IDs, relation semantics and canonical URLs". That is a genuine independent relationship check. It does not fix the wire form: the Guide is silent, and the source conflicts (Req 79/91 "association name" vs. the mapping-table footnotes' `ogc-rel:` prefix vs. unprefixed examples), so an author can choose either and pass their own edge list. F-11 stays a documentation/interpretation gap, not a missing check.

### New finding

**F-12 — "Independent" HTTP/conformance runner is asserted by adjective, not defined structurally**
- Severity/type: Medium, confirmed propagation gap with verification-independence consequences (to be examined further in Pass 5).
- Evidence: IDR-050 §6.3 requires that black-box cases "do not deserialize through the server's wire structs or call application services", expectations "derive from pinned standards … not current server output", and "server generated both sides" is prohibited; §18.1 lists "server and harness share models/logic → tautological passes" with required control "independent wire models and black-box release lane". Final report §17.1 repeats "independent wire models". The Guide carries only "The implementation's own serializers are not the sole judge" (`glaux-server-implementation-guide.md:23`) and "Encoder/decoder agreement alone cannot exclude a shared bug" (§8.1.1); its workspace has three crates (`glaux-domain`, `glaux-standards`, `glaux-server`) and no test/harness crate. Roadmap leaves 1.4.2, 1.4.6, 2.6.1, 3.5.1 say "independent HTTP fixtures/checks", "extend the independent runner", but no leaf establishes the runner or defines the independence rule.
- Failure scenario: the runner is written under `glaux-server/tests` and parses responses with `glaux_standards` types. A shared misreading (e.g., a wrong member name, a wrong `latest` rule, a wrong `rel` value) is encoded once and passes on both sides; mutation testing of server logic cannot detect a mistake located in the shared type.
- Contrary evidence: §8.1.1's assertion-strength rules, independent expected values, and the pinned external clients (OS4CSAPI, OWSLib) provide partial independence for the surfaces those clients touch.
- Smallest correction: state the structural rule once (Guide §8.1 or the first runner leaf): runner in its own crate/binary that does not depend on server or `glaux-standards` types for response interpretation; parse with generic JSON plus the pinned official schemas; expectations from the standard/fixture, never from a server response.
- Resolving evidence: crate dependency graph shows no server→runner or runner→server-types edge; one deliberate server-side schema misnaming fails the runner.
- Timing: before 1.4.2 (#19, first "independent HTTP fixtures" leaf; numbering per the Pass 1 mapping in which 1.4.3 = #20).
