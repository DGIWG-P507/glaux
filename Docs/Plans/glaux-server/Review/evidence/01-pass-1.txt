**F‑01 — No open‑source license exists or is scheduled**
- Severity: Medium. Confirmed omission.
- Evidence: Goal §7 ("released as open-source software", `glaux-server-goal-and-definition.md:194`); `glaux-server` main has no LICENSE; `glaux` main has no LICENSE. Roadmap 1.1.2, 1.2.1, 9.3.1 address *dependency* and *artifact* licenses only; no leaf selects or adds the project's own license.
- Consequence: 1.1.2's "dependency/license inventory" and 9.3.1's "license checks" have no compatibility target; 1.2.1's bundling of OGC schema artifacts with "license notices" cannot be reconciled with an undeclared project license; the open‑source claim is unsupported.
- Contrary evidence checked: none found in Guide §4.12 or Roadmap §6.
- Smallest correction: project lead selects a license (organizational decision), commits LICENSE to `glaux-server`, and adds "project LICENSE present and compatible with pinned dependencies" to 1.1.2's Done (issue #4).
- Resolves it: LICENSE file present; 9.3.1 checks against it.
- When: before #4 merges the first code. Not blocking #3.

**F‑02 — Nothing enforces the checks the plan relies on; assistant self‑merge is the only gate**
- Severity: High for this project's risk profile. Credible risk.
- Evidence: CONTRIBUTING "The assistant may merge after task-specific acceptance criteria, applicable checks and review pass. A separate human-approval pause is not mandatory"; "This policy does not itself configure branch protection, required reviewers or CI. Respect whatever controls actually exist." Roadmap §5.2 ([line 977](Docs/Plans/glaux-server/glaux-server-roadmap.md#L977)). No controls exist on `glaux-server`, and no leaf configures repository protection — 1.1.4 adds a CI *workflow*, which is code; making it *required* is a repository setting nobody owns in the plan.
- Failure scenario: a PR reports "tests passed" while the CI job was filtered/empty or never ran; the same assistant reviews and merges. Guide §8.1.1's "Prevent false‑green execution" ([line 950](Docs/Plans/glaux-server/glaux-server-implementation-guide.md#L950)) is procedural only.
- Contrary evidence: 1.1.4 requires demonstrating failure propagation — good, but it does not prevent merging on a red or absent check.
- Smallest correction: after #6 (1.1.4) lands, the project lead enables branch protection on `main`: require the CI status check, require branches up to date, block force‑push and direct pushes. Record this owner action in #6's Done or CONTRIBUTING.
- Resolves it: a deliberately failing PR is blocked from merge by GitHub, not by the assistant.
- When: before the first post‑CI code merge (#7 onward). Not blocking #3–#6.

**F‑03 — The authorization model is undefined, so disclosure tests cannot have independent expected answers**
- Severity: Medium. Unresolved question / deferred fundamental design decision.
- Evidence: Guide §4.10 ([line 590](Docs/Plans/glaux-server/glaux-server-implementation-guide.md#L590)) specifies an "access‑policy interface" and "configured caller/group/source permissions and resource relationships" but no policy schema: subjects, actions (read/write/task/report/subscribe/admin), scope granularity (family, System subtree, stream), inheritance (does System permission imply its datastreams/observations?), or how "source authority" binds to a token claim. - Consequence: the AI at #22 will invent the model; every later disclosure test (3.1.9, 3.5.5, 6.4.3, 7.3.4, 9.3.2) then derives its expected answers from that invention rather than from a documented rule — the exact "components built from the same assumptions" failure you asked me to look for. - Contrary evidence: Guide deliberately declines a "universal policy engine" — appropriate. A minimal declared model is not an engine.
- Smallest correction: add a short subsection to Guide §4.10 (or a note in #22) fixing the minimal policy vocabulary and the configuration file shape, with the two‑source fixture written as data before implementation.

- When: before #22. Not blocking Phase 1.1–1.3.
