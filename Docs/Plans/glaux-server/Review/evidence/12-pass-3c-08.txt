### 2. Security review — IDR-039 against Guide §4.10 (complete) and leaves #18–#23

The three qualifications you set are applied throughout: (i) everything below describes design text and leaf acceptance criteria, not executed verification — Pass 5 assesses whether the tests would actually prove it; (ii) "one admitted dispatch under concurrency" (Guide L580; 5.2.4) is never exactly-once physical execution — the Guide §6.4 L851 and IDR-029 §11.2 disclaim that, and status evidence from the executor remains the only proof of effect; (iii) offline authentication outcomes are whatever the explicit token/key-cache/trust policy says.

**Required safeguards — present as design text (no finding):**
- Deny by default and no fail-open when the policy service or verification is unavailable: `glaux-server-implementation-guide.md:594-596`; #22 acceptance ("assert no network-facing operation defaults to allow").
- Strict JWT validation (type, signature/algorithm, issuer, audience, validity, scopes; decoding ≠ authentication; no ID tokens as access tokens): L594 with RFC 9068/8725 — matches IDR-039 §8.1.
- Development identities loopback-only and rejected by network-facing configuration; anonymous read-only as an explicit option; CORS is not access control: L595 — matches IDR-039 §8.2's `unsafe-dev` intent without adopting its name.
- Authorize before queries, counts, extents, links, schema disclosure, latest selection, streaming; protect schemas, command capabilities, replay history like data: L596, L598 — matches IDR-039 §§9.2, 10.2, 14.
- Publisher/submitter/reporter authority separation; no `sender` impersonation: L596; §4.9 L574.
- No tokens/secrets/raw payloads in logs; committed accountability independent of sampled diagnostics: L600.
- **Offline authentication (#21):** the explicit policy is a bounded issuer-key cache with configured lifetime and refresh bounds; rotation, expired cached trust and issuer outage have "tested bounded behavior"; "do not… silently extend stale trust"; request-controlled URLs cannot trigger key fetching or fail-open. Consequence: a disconnected node rejects tokens once cached trust expires. That is the designed outcome, not a gap; IDR-039 §15's signed offline bundles and IDR-038 §13's offline command classes are optional mechanisms the Guide did not adopt. The only residual is whether DDIL deployment guidance states this consequence — to be checked against Guide §4.11 and its owning issues in Pass 4 before any finding.

**Optional research mechanisms — not adopted, not missing requirements:** sender-constrained tokens (mTLS/DPoP), backend-for-frontend selection, opaque-token introspection contract, IDR-039 §10.1's 24-action vocabulary (this is F-03's territory; unchanged), signed DDIL security bundles, a TLS 1.3 baseline statement (Guide L595 requires TLS or a documented trusted proxy without fixing a version — a profile choice, not a standards requirement).

**Effect on findings:** none new; F-03 unchanged. IDR-039 §3.3's warnings about CS-Go (no REST auth, permissive CORS) and OSH (optional auth) are consistent with the Guide's refusal to treat peer behaviour as a default.
